## 1. Scope & Normative References

This specification defines the **Continuous Restraint Conformance Suite (CRCS)** — the executable form of Invariant `I-5`. It is a CI gate: if any criterion fails, the change is non-conformant and CI exits non-zero with the criterion and surface named.

Normative references: ADR-0037 (D-2), `docs/proof-of-restraint/PLAN.md` §4 (I-1..I-5), [SPEC-RESTRAINT-PROOF-GENERATOR.md](SPEC-RESTRAINT-PROOF-GENERATOR.md), [SPEC-RESTRAINT-PROOF-VERIFIER.md](SPEC-RESTRAINT-PROOF-VERIFIER.md).

## 2. Formal Conformance Criteria

Each criterion is fail-closed, sandbox-isolated (`AIOSH_HOME` + temp `audit.db`, zero network), and asserted by named tests.

### C1 — Redeem-Gate Non-Bypassability (`I-2`, drift D1)
For every registered dispatch surface $S$ (Python MCP tool table, Rust MCP wire, CLI subcommands) and every consequential tool $t$:
$$\neg\,\exists\, \text{redeem row} \implies S(t) = \texttt{refused}$$
- C1.1: invoking a consequential tool with no minted grant ⇒ `refused`, **zero** audit rows of that tool's action type.
- C1.2: invoking with a minted-but-redeemed (spent) grant ⇒ `refused` (single-use enforcement).
- C1.3: any tool registered as consequential must appear in the redeem-gate coverage report; unknown consequential tools ⇒ **FAIL** (this is the "new tool additions" clause of `I-5`).

### C2 — Mint/Redeem Audit Parity (`I-1`, drift D2)
- C2.1: exactly one `pep.capability.mint` row per issuance; exactly one `pep.capability.redeem` per consumption.
- C2.2: rows carry `grant_token`, and canonical JSON (sorted keys, no whitespace) of the rows is byte-identical across substrates for the same scenario.

### C3 — Untouched-Grant Restraint Stability (`I-4`, drift D3)
For a grant $g$ never redeemed, across anchors $a_1, a_2$ bracketing window $[T_s, T_e]$:
$$\mathrm{verify}(\mathrm{prove}(g, T_s, T_e)) = \texttt{valid}$$
- C3.1: mint → anchors → prove ⇒ `verdict: PROVABLY_RESTRAINED`.
- C3.2: standalone verify of that proof with the anchor public key ⇒ `valid=true`, all 7 checks true.
- C3.3: idempotence — re-running prove/verify on the same state yields the same verdict.

### C4 — Touched-Grant Invalidation (drift D4, catastrophic direction)
$$\mathrm{redeemed}(g) \implies \mathrm{prove}(g) = \texttt{GRANT\_REDEEMED} \;\wedge\; \forall p \text{ claiming } g: \mathrm{verify}(p) = \texttt{invalid}$$
- C4.1: generator refuses with `GRANT_REDEEMED` (grant table and audit-ring redemption both detected).
- C4.2: any proof package asserting restraint for a redeemed grant fails one of the 7 verification gates (Bloom presence, chain mismatch, or grant redemption).

### C5 — Substrate Oracle Parity (drift D5)
- C5.1: Python and TypeScript produce identical `VerificationResult` (valid, reason code family, checks map) for the same fixture set, including hardened rejection fixtures.
- C5.2: canonical JSON serialization matches byte-for-byte across substrates.

### C6 — Anchor/Chain Continuity (`I-3`)
- C6.1: `append_anchor` at deterministic cadences ⇒ `verify_checkpoint` passes for every anchor and the chain verifies (`aiosh anchor verify`).
- C6.2: for consecutive anchors $a_i, a_{i+1}$ used in C3: $T_{a_i} \le T_s < T_e \le T_{a_{i+1}}$ and $seq_i \le seq_{i+1}$.

## 3. Scenario Fixtures

| Fixture | Setup | Expected |
|---|---|---|
| `F-UNTOUCHED` | mint `gr_conform_01`, 2 anchors, window inside, no redeem | C3: prove+verify valid |
| `F-REDEEMED` | mint `gr_conform_02`, redeem before window end | C4: prove refused; forged proof verifies invalid |

| `F-NO-GRANT` | consequential tool, no grant | C1.1: refused |
| `F-PARITY` | fixed mint/redeem payloads | C2/C5: identical canonical rows & verdicts across substrates |
| `F-ANCHOR-CADENCE` | 3 anchors at fixed seqs | C6: chain verifies, bounds hold |

Fixtures are deterministic: fixed keys (`generate_keypair` output pinned per run), fixed ISO-8601 UTC timestamps, fixed grant ids.

## 4. Harness Interface & CI Contract

- **Suite**: `code/aiosh-mcp/tests/test_por_conformance.py` — scenario tests C1..C6 (pytest).
- **Battery runner**: `tools/test_por_conformance_suites.py` — criteria report `C1..C6 PASS/FAIL`, mirroring `tools/test_fs_layout_suites.py` style.
- **CI registration**: the suite MUST be registered in `tools/ci_suites.py` (order IS CONTRACT) so `bash ci/run_all_smokes.sh` enforces `I-5`; run summary lands in `$AIOSH_CI_RESULTS` and passes `tools/ci_service.py check`.
- **Manifest**: `docs/proof-of-restraint/CONFORMANCE.md` maps each criterion → test node id → evidence file. Auditors read exactly one document.
- **Failure envelope**: every failure names criterion id, surface, and observed vs expected; exit code non-zero.

## 5. Acceptance Criteria (binding on T-02884..T-02891)

1. All six criteria C1..C6 have at least one automated test each, executed in CI.
2. The D4 direction (redeemed grant verifies as restrained) is impossible under the suite — proven by C4 fixtures.
3. Coverage report lists every registered consequential tool (C1.3) with no gaps.
4. Python/TypeScript parity assertions (C5) run in the same CI invocation.
5. `CONFORMANCE.md` manifest is complete and links each criterion to passing evidence.
