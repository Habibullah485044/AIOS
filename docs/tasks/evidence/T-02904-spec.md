## 1. Scope & Non-Goals

**In scope**: how an operator or agent selects *where the compliance store lives*, *how large it
may grow*, *how many entries it may hold*, and *whether config mutations are gated and audited* —
across both substrates (Python/MCP and Rust/CLI).

**Non-goals**:
- Does not change the store schema (`ComplianceCatalogSnapshot {version, mappings, generated_at}`).
- Does not change the 7 existing verbs (`list|show|register|status|assess|check-pep|init`).
- Does not change string bounds (ID ≤ 64, title ≤ 128, desc ≤ 2048, notes ≤ 2048, threats ≤ 16,
  tags ≤ 16) — these are parity-tested contract values, not operator knobs.
- Does not repair `T-02741-configuration-research.md`'s mis-citations (deferred as D-7 there).

## 3. Contract

### 3.1 Configuration model

```rust
// [NEW] ⟦AIOS⟧ code/aiosh-rust/aiosh-core/src/compliance_config.rs
#[derive(Debug, Clone, PartialEq, Eq, Serialize, Deserialize)]
#[serde(default)]
pub struct ComplianceConfig {
    pub version: String,              // "1.0.0"
    pub store_path: PathBuf,          // default "docs/compliance_map.json"
    pub max_store_file_bytes: u64,    // default 1 MiB, bounds [4096, 16 MiB]
    pub max_entries: usize,           // default 1024, bounds [1, 4096]
    pub audit_all_queries: bool,      // default false (see §6 D-4)
    pub audit_all_mutations: bool,    // default true (must never be false — §6)
}
```

Python mirror: `aiosh_mcp/compliance_config.py` exposing `load_config(path=None) -> dict`,
same field names, same bounds — mirroring the existing `release_config.py` **[REUSED pattern]**
(`aiosh_mcp/release_config.py:25-45`).

### 3.2 Precedence (resolved exactly as T-02903 D-1/D-3)

1. **Explicit argument** — CLI `--path <P>` (existing) wins over everything for the store path.
2. **Environment** — `AIOSH_COMPLIANCE_CONFIG` → config file at that path; then
   `AIOSH_COMPLIANCE_MAP_PATH` → `store_path` override. Both must pass the hygiene check in §4.3.
3. **Config file** — at `AIOSH_COMPLIANCE_CONFIG`, else `docs/compliance_config.json`.
4. **Compiled defaults** — the literals in §3.1.

This is the *same* cascade as `ThreatModelConfig::from_env()` (`threat_model_config.rs:136-158`),
including "invalid value → fall back to defaults, never panic".

**Cross-substrate rule (fixes T-02903 F-3):** the Rust CLI must resolve the store path through
this same cascade, i.e. it must read `AIOSH_COMPLIANCE_MAP_PATH` and `AIOSH_COMPLIANCE_CONFIG`.
Today `cmd_compliance` reads neither (verified: 0 occurrences), so the two substrates can
disagree about which file is the authoritative compliance store. After this spec, both substrates
resolve identically, and `--path` remains the strongest override on the CLI.

### 3.3 CLI surface (new)

```
aiosh compliance config show  [--json] [--path P] [--config C]
aiosh compliance config init  [--force]        [--path P] [--config C]
```

- `show` — read-only; prints the **resolved** config with a `source` field per key
  (`argument | env | file | default`). Read path: no grant, no store write.
- `init` — writes `docs/compliance_config.json` only; refuses to overwrite unless `--force`.
  PEP-gated write (§6) and emits exactly one audit row.

Existing 7 verbs are unchanged; they simply consume the resolved config.

### 3.4 MCP surface (new actions on the existing tool)

Added to the existing `aios_compliance` action dispatch (`server.py:792+`) — **no new MCP tool**:

| action | grant | reads store | writes | audit |
|---|---|---|---|---|
| `config-show` | no | no | no | one row (query) |
| `config-init` | **yes** | no | config file only | one row (write) |

Both go through the existing `_recorded_call` with
`require_grant = action in compliance_mod.WRITE_ACTIONS` — so `WRITE_ACTIONS` gains
`"config-init"` (and **not** `"config-show"`). Envelope and error shape are unchanged
(`{ok, action, error, audit_id}` per spec §4 of T-02894).

## 4. Inputs / Outputs / Errors / Persistence

### 4.1 Happy path

**Input** (CLI): `aiosh compliance config show --json`
**Output**: HTTP-free JSON envelope, `ok:true`, `data: {version, store_path, max_store_file_bytes,
max_entries, audit_all_queries, audit_all_mutations, source: {store_path: "env", ...}}`
**Persistence**: none (read-only).

**Input** (CLI): `aiosh compliance config init --json`
**Output**: `ok:true`, `data.path` = the written config path, `data.created` = true|false (false
when `--force` replaced an existing file).
**Persistence**: creates/overwrites **only** the config file (§5.1). The store
`docs/compliance_map.json` is untouched — `init` for the *store* remains the existing
`aiosh compliance init` verb.

### 4.2 Failure paths (error cases, exact codes)

| Condition | Code | Substrate behavior | Store touched? |
|---|---|---|---|
| config path empty / contains `..` / control chars / >1024 bytes | `COMPLIANCECONF_ERR_PATH_TRAVERSAL` | fall back to defaults, record `source=config-invalid` | no |
| config path is a symlink | `COMPLIANCECONF_ERR_PATH_TRAVERSAL` | fall back to defaults (same rule) | no |
| config file > 64 KiB | `COMPLIANCECONF_ERR_FILE_SIZE` | fall back to defaults | no |
| config file malformed JSON | `COMPLIANCECONF_ERR_PARSE` | **fail closed** → `ok:false`, no store mutation | no |
| numeric field out of bounds | `COMPLIANCESVC_ERR_BOUNDS`-equivalent `COMPLIANCECONF_ERR_BOUNDS` | clamp to nearest bound, report `source` | no |
| `store_path` resolves to a non-`.json` path | `COMPLIANCESVC_ERR_PATH_TRAVERSAL` | **fail closed** on any store op | no |
| store exceeds 1 MiB on save | `COMPLIANCESVC_ERR_FILE_SIZE` (existing) | save rejected, prior file intact | unchanged |
| store exceeds `max_entries` on register | `COMPLIANCESVC_ERR_CAPACITY_EXCEEDED` (existing) | register rejected | unchanged |
| `config-init` without a grant | PEP refusal envelope (existing) | action refused, refusal row written | no |
| config file missing entirely | *not an error* | defaults, `source=default` | no |

**Rule**: *inert* fields (bounds, capacity) degrade (clamp/default); *security-relevant* fields
(`store_path` validity, malformed file) **fail closed**. This resolves T-02903 D-5.

### 4.3 Environment-variable hygiene (CWE-15 control)

Before an env value is accepted it must satisfy: non-empty, no `..`, no control characters,
`len <= 1024` — byte-for-byte the `threat_model_config.rs:139` predicate. A value failing this
predicate is **ignored** (defaults apply) and the resolution reports
`source: "env-invalid"` rather than silently succeeding with an unvalidated path. The store path
*always* re-enters `validate_path()` before any read/write, so config can never become a second,
weaker path gate (CWE-22/CWE-59).

### 4.4 Persistence effects summary

| Action | Config file | Store file | Audit rows |
|---|---|---|---|
| `config show` / `config-show` | read-only | untouched | 1 (query) |
| `config init` / `config-init` | create/replace | untouched | 1 (write) |
| `list`/`show`/`assess`/`check-pep` | read-only | read-only | 1 (existing) |
| `register`/`status`/`init` (store) | read-only | mutated | 1 (existing) |

Config file writes use the same atomic write discipline as sibling configs (PID-tagged temp file
+ rename), so a crash mid-write cannot leave a truncated config.

## 5. Constraints

1. **Config file cap = 64 KiB** (`MAX_CONFIG_FILE_BYTES`), matching
   `audit_chain_config.rs:35`, `capability_config.rs:11`, `doc_index_config.rs:10`. Independent of
   the 1 MiB store cap (CWE-400).
2. **Store cap stays 1 MiB** and `max_store_file_bytes` may only *lower* it — a config cannot
   raise the hard cap above 16 MiB, and cannot disable it.
3. **String bounds are not configurable** (parity contract; see Non-Goals).
4. **`audit_all_mutations` cannot be set to false.** Config load must reject/clamp it to `true`
   — silently disabling mutation auditing would violate the one-row-per-call invariant that
   `_recorded_call` guarantees (`server.py:62-92`).
5. **Reads never create the store.** Unchanged from T-02894 §; config reads likewise never
   create a config file (`show` is pure).
6. **Both substrates must resolve identically** — cross-substrate byte parity of the resolved
   config is asserted by test (§7).

## 7. Testable Assertions (contract, not implementation)

1. `config show --json` with no config file → all defaults, `source=default`, exit 0, **store
   file does not appear**.
2. `AIOSH_COMPLIANCE_MAP_PATH=/tmp/x.json` → **both** Rust and Python resolve `/tmp/x.json`;
   identical `store_path` and identical `source` on both substrates.
3. `AIOSH_COMPLIANCE_MAP_PATH="../etc/x.json"` → ignored; resolution falls back to the default
   and reports `source=env-invalid`; a subsequent store op still passes through `validate_path`.
4. Config file of 65,537 bytes → `COMPLIANCESVC_ERR_FILE_SIZE`/`COMPLIANCECONF_ERR_FILE_SIZE`,
   defaults used, no crash.
5. Config file `{bad json` → `ok:false` with `COMPLIANCECONF_ERR_PARSE`, store untouched.
6. `max_entries: 999999` → clamped to 4096 with `source=config`; `max_store_file_bytes` above
   16 MiB → clamped.
7. `audit_all_mutations: false` → loaded as `true` (rejected), reported in `source`.
8. `config-init` without grant → refusal envelope, exactly one audit row, config file absent.
9. `config-init` with grant → config written atomically, exactly one audit row, store untouched.
10. `--path` beats env beats file beats default (precedence ladder, §3.2).

## 8. Honest Limitations

- This is a **specification only** (task acceptance: no code changed). Sections 3–5 are
  proposals marked ⟦AIOS⟧ until T-02905 (Scaffold) and T-02906 (Implementation) land.
- No upstream/open-source project provides a `ComplianceConfig`; the shape is AIOS-specific,
  deliberately copied from this repo's own `ThreatModelConfig` precedent.
- Multi-tenant store isolation (T-02903 "explicitly unknown") is **not** addressed here; a
  single resolved store path per process remains the contract.
- §3.4 assumes `_recorded_call`'s `require_grant` derivation accepts an extended `WRITE_ACTIONS`
  without other changes; if the gate rejects new action names, the MCP verbs must be re-mapped in
  T-02905 rather than invented differently.
